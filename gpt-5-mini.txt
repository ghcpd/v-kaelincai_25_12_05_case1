**4) New System Design — Greenfield Replacement**

Goal: A resilient, idempotent, observable appointment booking system with safe migration paths.

High-level goals:
- Strong idempotency for create operations.
- Reliable delivery to calendar via transactional outbox.
- Clear state machine for appointment lifecycle (init -> pending -> confirmed/failed -> compensated).
- Retriable external calls with bounded exponential backoff and circuit breaker.
- Auditability via structured logs and events.

4.1 Capability boundaries and service decomposition
- API Gateway / Ingress (HTTP)
  - Accepts client requests (create appointment, read status, cancel).
  - Validates payloads and enforces idempotency key header.
- Appointment Service (stateless, REST/GRPC)
  - Orchestrates appointment lifecycle; writes to authoritative DB.
  - Enforces schema/field validation.
  - Emits outbox events transactionally.
- Outbox Worker / Delivery Service
  - Reads durable outbox and delivers to external calendar (with retries/backoff).
  - Marks events as delivered or failed.
  - Uses circuit breaker to protect from downstream outages.
- Calendar Integration Adapter
  - Encapsulates call details, token management, mapping of errors.
- Notification Service (optional)
  - Sends notifications on success/failure.
- Observability Platform
  - Logging, tracing (trace/request id), metrics (counters, histograms), health checks.

4.2 Unified state machine (appointment)
- States:
  - created (persisted, awaiting calendar)
  - sending (outbox worker picked up)
  - confirmed (calendar success)
  - failed (calendar permanently failed)
  - cancelled (user cancelled)
- Transitions:
  - created -> sending (worker picks up)
  - sending -> confirmed (calendar success)
  - sending -> failed (after retry exhaustion)
  - failed -> compensated/cancelled (manual or automatic compensation)
- Idempotency: idempotency_key -> appointment_id mapping stored; create returns existing appointment if exists.

4.3 Idempotency, retry, timeout, circuit breaker, compensation
- Idempotency:
  - Require client `Idempotency-Key` header (or derive from authenticated token + payload hash).
  - DB-level unique constraint on `idempotency_key`.
  - Create operation is PUT-like: create if absent, else return stored.
- Retry/backoff:
  - Delivery worker uses exponential backoff with jitter, e.g. base 200ms, factor 2, max attempts 5.
  - Persist attempt counts per outbox entry for observability.
- Timeout:
  - Downstream calls have short client-side timeouts (e.g., 2s).
  - Worker-level overall time budget for an attempt.
- Circuit-breaker:
  - Per external service circuit breaker with sliding window and thresholds (e.g., open if failures > 50% in last 1m and min 20 calls).
  - When open: worker immediately mark as delayed and postpone attempts; metrics for dashboard.
- Compensation:
  - Use Saga pattern: if calendar booking fails permanently, run compensation actions (delete internal provisional booking or mark as failed and notify).
  - For critical side-effects, implement reversible operations (e.g., cancel calendar entry if partial).

4.4 Architecture and data flow (ASCII diagram)

API Client
   |
   | HTTP POST /appointments (Idempotency-Key)
   v
API Gateway -> Appointment Service (validate)
   |
   | Begin DB transaction:
   |   - insert appointment if idempotency_key not present
   |   - insert outbox event (appointment.created)
   | Commit
   v
Outbox (DB table)  <-- durable
   |
Outbox Worker (poll or stream)  --[retry/backoff, circuit-breaker]--> Calendar Adapter -> Calendar API
   |
   +- success -> mark appointment confirmed, clear outbox
   +- failed retry -> increment attempt count, leave outbox
   +- final fail -> mark appointment failed, emit appointment.failed event

4.5 Key interfaces / Schemas

API: POST /v1/appointments
- Headers:
  - `Idempotency-Key`: string, max 255 chars, required.
  - `X-Request-ID`: optional unique request identifier.
- Body (JSON):
  - `when`: string, RFC3339 timestamp, required.
  - `user_id`: string, required (UUID).
  - `details`: object, optional (max 2000 chars).
- Response:
  - `appointment_id`: string UUID.
  - `state`: enum [created|sending|confirmed|failed|cancelled].
  - `created_at`: timestamp.
  - `idempotency_key`: echoed.

DB Appointment Table (example)
- id: UUID PK
- idempotency_key: varchar(255) UNIQUE NOT NULL
- user_id: UUID
- when: timestamptz NOT NULL
- payload: jsonb
- state: varchar(32) NOT NULL
- created_at: timestamptz
- updated_at: timestamptz

Outbox Table
- id: UUID PK
- appointment_id: UUID (index)
- event_type: varchar
- payload: jsonb
- attempts: int default 0
- next_attempt_at: timestamptz (for delayed retry)
- max_attempts: int
- created_at, updated_at

Calendar API Contract (adapter-local)
- Request to calendar:
  - request_id (string <= 64)
  - when (RFC3339)
  - metadata (user, details)
- Responses:
  - 200 OK: { calendar_id: string, status: scheduled }
  - 4xx: client error -> treat as permanent failure (no retry) unless transient
  - 5xx / network error: transient -> retry

Validation rules
- `when` must be in the future (>= now + 1 minute) or within allowed window.
- `details` length <= 2000 chars.
- `idempotency_key` regex: [A-Za-z0-9-_]{1,255}

4.6 Migration & parallel run

Objective: Move from legacy system to new system with minimal disruption.

Approach options:
A) Shadow write + read-forward
  - Start by deploying new Appointment Service and Outbox Worker.
  - For incoming requests at API gateway, dual-write to legacy and new system (or route to new system while keeping legacy read-only).
  - Compare responses and reconcile differences; use sampling.

B) Read from legacy DB into new system
  - Backfill existing appointments into new DB with mapping of old IDs to new ids and preserve idempotency keys if present.
  - Replay outbox events for pending appointments.

Recommended procedure:
1. Deploy new service and outbox worker in parallel with monitoring (canary).
2. Shadow traffic: API gateway sends copies to new service. New service logs diffs and emits reconciliation metrics.
3. After validation, switch reads to new service; keep legacy write disabled or re-routed.
4. For write cutover:
   - Option 1: Change clients to include Idempotency-Key (recommended).
   - Option 2: Implement deduplication in new service that maps legacy request properties to dedupe key.
5. Backfill: replay legacy appointments into new outbox if needed for pending operations.
6. Rollback plan: restore traffic routing to legacy if errors observed; ensure both states are reconciled.

4.7 Rollback paths
- Route traffic back to legacy API gateway.
- Use reconciliation process to reconcile writes during failed cutover period. Outbox events should be idempotent to allow safe replay.
