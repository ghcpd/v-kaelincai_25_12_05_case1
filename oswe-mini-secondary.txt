## 3.4 New System Design — high level (Greenfield)
Goal: Safe deterministic routing, clear contracts & observability, idempotency, robust retry & failure handling.

High-level components:
- API Gateway / Frontend (accepts route requests, verifies auth, enforces idempotency keys).
- Router Service (core logic, algorithm selection: Dijkstra / Bellman-Ford).
- Graph Store (persistent authoritative graph; could be relational DB, graph DB, or object-store snapshot).
- Outbox + Worker (guaranteed downstream eventual delivery for notifications & reconciliation).
- Audit & Reconciliation Service (asynchronous checks and audits).
- Observability & Tracing (structured logs, request/trace IDs, metrics).

ASCII architecture:
API Gateway -> Router Service -> Graph Store
                       ↘ Outbox -> Worker -> Audit
                       ↘ Metrics & Tracing

Design principles:
- Validate preconditions (reject negative weights unless Bellman-Ford is chosen).
- Idempotency: each request may contain an idempotency_key; store results so retrying returns same output.
- Retry strategy: client retries with exponential backoff; service enforces per-request timeouts and has a circuit breaker to protect downstream or heavy compute.
- Transactions: Use outbox pattern to atomically persist results + side-effect publishes.
- Compensation / Saga: If multi-step flows fail, provide compensating actions or rollback steps via a Saga orchestrator.

Data flow (example):
1. Client -> POST /route {start,goal,algo, idempotency_key}
2. API validates & checks cache / idempotency store.
3. Router chooses algorithm:
   - If graph has negative edges -> Bellman-Ford (or error if not allowed)
   - Else -> Dijkstra
4. Compute -> persist event to outbox (audit + downstream notifications)
5. Worker drains outbox and publishes events reliably.

Key interfaces / schema examples

- Request payload (API):
{
  "start": "A",
  "goal": "B",
  "algorithm": "auto",          // auto | dijkstra | bellman-ford
  "idempotency_key": "abc-123"
}
Field constraints:
- start, goal: String, 1..50 chars, must be present
- algorithm: enum(auto, dijkstra, bellman-ford)
- idempotency_key: optional string, recommended UUID v4

- Response:
{
  "request_id":"req-<ts>-<rand>",
  "path": ["A","C","B"],
  "cost": 4.0,
  "algorithm": "dijkstra",
  "timestamp": 12345.123
}

Validation:
- Data types validated; graph presence checked; if negative edges present and algorithm==dijkstra → ValueError/400.

Migration & parallel run strategies
- Shadow traffic: Deploy new Router v2 side-by-side; route small % traffic by shadowing requests to Router v2 while responses are compared to legacy.
- Dual-write/cutover: For slow migrations, write results to both systems and gradually shift traffic.
- Backfill: Snapshot graphs into new Graph Store; backfill historical IDs to ensure reconciliation.
- Rollback: Keep feature toggles and runtime config to route traffic back to legacy if mismatch % exceeds threshold.
- Roll-forward: use canary releases with health and correctness monitors.
